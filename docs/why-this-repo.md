# 왜 이 저장소인가 — 팀에서 비어 있던 칸, 그리고 이게 포트폴리오로 서는 이유

이 문서는 두 질문에 답한다. **왜 팀 프로젝트 안에서는 이걸 안 했나**, 그리고 **그래서
이 저장소가 무엇을 보여주나.** 앞 질문의 근거는 전부 팀 저장소
[SAJOYO/DAENGS_dev](https://github.com/SAJOYO/DAENGS_dev) `origin/dev` 에서 인용했다
(2026-09-24 fetch, 마지막 커밋 `c172b4a4` 2026-09-21). 팀 코드는 읽기만 했고 고치지 않았다.

팀 버전의 피부 오케스트레이션(D-079)은 **내가 쓴 것**이다. 그러니 아래는 "팀은 못 했고
나는 했다" 가 아니라, **같은 사람이 1편에서 멈춘 자리와 2편에서 넘은 자리**다.

## 한 줄

팀 버전에서 오케스트레이터는 **이미 끝난 판정의 기록**(`verdict` + `days_ago`)을 해설했고,
사진은 앱이 따로 올렸다. 여기서는 **사진이 루프 안으로 들어와** 근거 검색과 한 턴에서 합쳐진다.
그 대가로 모델이 보는 것이 늘고(계열 · 확률), 늘어난 만큼을 **코드 게이트 8개**로 갚는다.

## 팀에서 이 칸이 비어 있던 이유 — 다섯 가지, 전부 기록에 있다

### 1. 설계로 정한 것이었다 — "대화로 사진은 안 받는다"

`docs/orchestration/architecture.md` (CONFIRMED 절):

> **multipart 이미지·영상 워크플로는 전용 API 에 남습니다.** 대화로 "피부 사진 봐줘"가
> 들어오면 실행이 아니라 해당 업로드/UI 플로우로 **HANDOFF** 합니다.

같은 문서의 능력 준비도 표에서 Skin 은 **"HANDOFF 만 · 전용 multipart 업로드 UI/API —
오케스트레이터가 실행하지 않음"** 이고, 바로 아래에 이유가 한 줄 더 있다:

> Skin 이 main backend 에서 기술적으로 호출 가능해진 것은 **런타임 사실의 변화**이지
> Card 1 역할의 변화가 아닙니다. multipart 이미지 획득과 통제 문구 보존이 필요한 전용
> 플로우라 대화 진입은 계속 HANDOFF 입니다.

인가 매트릭스(D-036, 2026-08-30 사람 승인)도 같은 말을 한다 — *"v1 은 Training·Life·Walk 를
앱 회원·관리자 모두에게, **Skin·Gait EXECUTE 는 아무에게도 허용하지 않습니다.**"*

즉 "안 만든 것" 이 아니라 **"만들지 않기로 한 것"** 이었다. 그 결정 위에 앱 · 백엔드 · 라우터가
쌓였다 — 앱은 그 HANDOFF 를 받아 촬영 화면을 여는 쪽으로 만들어져 있다.

### 2. 라우터 벤치마크가 그 결정을 얼려 놓았다

`backend/evals/orchestration_router/phase2_v11_report.md` (2026-09-07, PASS). 골드 80문항 · 게이트 15개.
그중 하나:

| Metric | Actual | Gate |
| --- | ---: | ---: |
| `skin_handoff_recall` | 1 | **>= 1** |

피부 신호는 **반드시 HANDOFF** 여야 통과한다. 사진을 EXECUTE 로 열면 이 게이트가 **정의상**
깨진다 — 라우터가 틀려서가 아니라 정답이 바뀌어서. 골드셋을 다시 짜고, v1~v11 로 쌓인 리포트의
비교 기준을 다시 세워야 한다. 그래서 D-081 은 *"라우터 · `ExecuteName` **무변경** — 라우터의
판단을 바꾸는 것이 아니라, 그 판단이 HANDOFF 일 때 목적지만 바꾼다"* 로 갔다. 라우터를 안 건드리는
것이 그 시점의 올바른 선택이었다.

### 3. 계약이 사진을 받을 수 없게 생겼다 — 일부러

`orchestration/contracts.py`:

```python
class SkinPayload(ContractModel):
    """**병변 이름 · 확률 · 통제 문구의 칸이 없는 것이 이 타입의 전부다** (불변식 15, D-023)."""
    question: str
    screening: ScreeningContext          # {verdict, days_ago}
    history: ScreeningHistory | None
    conversation: ConversationContext | None
```

모델이 받는 판정은 `verdict` 와 `days_ago` **둘뿐**이다. 프롬프트(`adapters/skin.py`)도 그렇게 말한다 —
*"The only facts you have are in SCREENING: verdict and days_ago."* 이건 D-023 의 결과다: 2단계 병변명이
holdout 에서 **56.6% 틀려서** 응답 계약에서 1등 필드를 아예 뺐고, 그 계약을 오케스트레이션까지
이어 온 것이 불변식 15 다. **칸이 없으면 프롬프트로도 되돌릴 수 없다** — 게이트보다 강한 방어다.

`planner.py` 의 `_EXECUTE_NAMES` 가 `skin` 을 빼는 이유도 주석에 있다: *"넣는 순간 기록 없는 `skin`
신호가 HANDOFF 대신 payload 규칙 없는 EXECUTE 가 되어 500 이 난다."* 사진을 받는 payload 를 새로
설계하지 않는 한 넣을 수 없다.

### 4. 배포 형태가 동기 대화와 안 맞았다

`architecture.md`: Skin 은 별도 서비스가 아니라 **`backend` 한 프로세스 안의 라우터**(`/screen/v1/screen`,
D-040)다. 가중치는 첫 요청에 지연 로딩, 컨테이너의 torch 는 CPU 판(`pyproject.toml` 주석 — "서버 backend
컨테이너는 CPU"). 그리고 *"옛 `/screen/v1/screen` 라우터는 현재도 인증·rate limit 이 없어 보안 후속은
별도(#239 Hold)"*. 대화 루프가 그 라우터를 툴로 부르려면 앱 계약(multipart) · 인증 · CPU 추론 지연
셋을 같이 손대야 했다. 여기서는 서브에이전트를 **자기 venv 의 stdio 프로세스**로 떼어 그 셋을 우회했다 —
팀 서버에는 붙지 않는다.

### 5. 닷새가 남아 있었다

D-079 는 **2026-09-16** 이다. 팀 `dev` 의 마지막 커밋은 **2026-09-21**. 그 닷새 안에 같은 날 후속 결정
셋(D-081 · D-082 · D-083)이 붙었다 — 이어 묻기 라우팅, 앞 대화 보기, `general` 폴백 가로채기. 전부
**기록 위에서 해설하는 길을 넓히는** 일이었고, 사진을 안으로 들이는 일은 그 크기가 아니었다.

### 그리고 재 보니, 그 구조에서는 에이전트가 룰과 같았다

이게 이 저장소의 출발점이다. D-081 의 첫 문단:

> **재 보니 그 구조에서는 에이전트가 룰과 같았다.** 실제 Gemini 180셀을 돌린 결과, 최종 행동이
> 판정별로 완전히 고정이었고(normal 지켜보기 33/33 · abnormal 진료 33/33 · retake 다시 찍기 36/36),
> 같은 입력 3회 반복은 글자까지 같았다.

모델이 `verdict` 하나만 보니 **결정할 것이 없었다.** 안전은 완벽했고(안전 위반 0/102) 그만큼 모델이
하는 일도 없었다. 그러면 질문은 하나로 좁혀진다 — **모델에게 더 주면 무엇이 되고, 그 대가를 어떻게
갚나.** 팀 일정 안에서는 던질 수 없는 질문이라 개인 저장소에서 던졌다.

## 여기서 넘은 것

| | 팀 (D-079) | 여기 |
| --- | --- | --- |
| 사진 | 앱이 찍고 앱이 `/screen` 호출 | 오케스트레이터가 MCP 툴로 직접 |
| 사진 + 행동 질문 | 한 턴에 안 합침 | 한 턴에서 합침 |
| 모델이 보는 판정 | `verdict` + `days_ago` | verdict + 계열 + 확률 (6종 이름만 제거) |
| 이름 방어 | 계약에 칸이 없음 + `speaks_beyond_screening` 문장 교체 | `_for_model` 제거 + G1 차단 + 고쳐쓰기 + 조립 |
| 모델의 결정 | 없음(행동 고정) | 상담 툴을 부를지, 무엇을 옮길지 — 그래서 게이트가 실제로 걸린다(60턴 중 12) |

**팀 버전이 더 강한 방어다.** 여기는 개선판이 아니라 **더 주고 게이트로 갚은 판**이다. 값한
교환이었는지는 `evals/` 가 말한다 — 첫 초안 걸림 12/60, 최종 위반 0, 판정기가 잰 판정 충실 47/47.

## 이게 포트폴리오로 서는 이유 — 에이전트 개발자로서 보여주는 것

이 저장소의 목적은 **에이전트 개발**이다. 프레임워크를 얹은 데모가 아니라, 루프 · 툴 · 서브에이전트 ·
안전 · 평가를 **직접 설계하고 실측으로 고친** 기록이다. 면접관이 "에이전트를 만들어 봤나" 라고 물으면
아래를 하나씩 짚으면 된다.

- **에이전트 루프를 직접 썼다.** 툴 선택 → MCP 호출 → 초안 → 게이트 → 고쳐쓰기 → 조립 (`loop.py`).
  왕복 상한, 고쳐쓰기 한 번, 두 번째는 LLM 을 빼는 갈래까지 전부 코드다. 프레임워크 의존 없음.
- **서브에이전트를 MCP stdio 로 붙였다.** 각자 자기 venv 의 프로세스라 torch 와 bge-m3 가 안 다투고,
  하나가 죽어도 나머지로 답한다(실측 C5). 툴 스키마의 `anyOf` 가 Gemini 에서 400 을 내는 것,
  `structured_content` 없이 글자로 오는 서버, 빈 환경변수가 자식을 죽이는 것 — 붙여 본 사람만 아는 것들.
- **결정론적 신호는 라우터에게 안 맡긴다.** 사진 유무는 코드가 소비한다 — 있으면 무조건 부르고, 없으면
  툴 목록에서 뺀다. 로컬 7B 실측에서 제일 흔한 실수 둘이 그거였다. 가짜 assistant tool_call 을 끼우면
  Gemini 가 400 을 내서 사용자 메시지 본문에 넣는다 — 공급자마다 다른 길은 길이 아니다.
- **툴 결과를 모델에게 주기 전에 깎는다.** 6종 이름이 실린 자리(`distribution` · `labels`)를 중첩 어디서든
  뗀다. 프롬프트로 참게 하는 것보다 안 주는 게 싸고 확실하다. 게이트는 마지막 그물이다.
- **멀티턴.** 앞 턴의 판정을 다음 턴이 들고 다니고 게이트도 그걸 본다. 앞 대화는 상한을 두고 넘긴다.
- **모델을 갈아 끼울 수 있다.** OpenAI 호환 한 규격으로 Gemini · Ollama · LM Studio. 로컬 후보 4종을
  실제 시스템 프롬프트와 툴 스키마로 프로브해 둘을 남겼고, `max_tokens` 를 안 보내던 것을 거기서 잡았다.
- **안전을 프롬프트가 아니라 코드에 뒀다.** `gates.py` 8개, 테스트 130개, 트리거는 "켜기만 하고 끄지 않는다".
  면책 · 행동 권고 · 판정 문장은 코드가 붙인다 — 부탁한 것은 잴 수 없고 붙인 것은 잴 수 있다.
- **평가를 세 축으로 갈라 잰다.** 라우팅(3회 전 회차) · 게이트(결정론) · 적대적(실제 모델). 그리고
  LLM-as-judge 를 사람 라벨로 보정했다(71% → 98%). 평가가 실제로 잡은 것: "빨개져요" 를 놓친 G5,
  찾아보지 않고 "자료에 없다" 고 한 G6, 막대를 읽고 계열을 단정한 G7, JSON 강요에 판정 문장을 뺀 것.
- **틀린 것을 지우지 않았다.** 11/15 → 15/15 에서 둘은 평가가 틀린 것, 27/30 에서 둘은 기대값이 틀린 것,
  판정기 보정 98 → 93 → 98 은 픽스처 탓. 무엇을 왜 옮겼는지가 표로 남아 있다.
- **돌아간다.** 라이브 데모(HF Space, ZeroGPU 위 FastAPI) · 정적 뷰어(실제 트레이스) · 3분 데모 모드 ·
  CI(ubuntu · windows · mcp 1.x · docker) · 회귀 기준선.

요점은 라우팅이 아니라 **모델이 말해도 되는 것을 코드가 정한다**는 것 — 그게 이 에이전트를
다른 툴콜링 에이전트와 가르는 한 줄이고, 위 항목들이 그 한 줄을 받치는 개발이다.

## 약한 곳 — 물으면 이렇게 답한다

- **라이브 데모는 스텁이다.** 진짜 모델(1.2GB 가중치 · bge-m3 · pgvector)은 로컬에서만 돈다. 데모에서
  진짜인 건 오케스트레이터 · 게이트 · 고쳐쓰기 · 조립 · 트레이스이고, 상담 본문과 판정은 고정값이다.
  정적 뷰어의 트레이스는 진짜 모델로 돌린 것이다.
- **판정기와 피판정 모델이 같은 계열이다.** Gemini 가 Gemini 를 채점한다. 다른 계열 판정기(granite 8B)를
  보정해 봤는데 78% 로 기준 아래였다. 그래서 "보정 98%" 는 "사람 13건과 98% 일치" 이지 독립 심판이 아니다.
- **평가셋이 작고, 내가 만들고 내가 라벨했다.** 라우팅 30 · 적대적 20 · 보정 13. 팀 라우터 벤치마크가
  골드 80 에 게이트 15 인 것과 견주면 얇다. 숫자는 경향이지 정밀도가 아니다.
- **라우팅은 LLM 이 한다.** 사진 유무만 코드가 소비하고 나머지는 모델이 고른다. 회차마다 다르고, 그래서 3회
  전 회차를 적는다. 로컬 7B 는 사진 + 상담 한 턴을 못 한다.
- **무료 티어 위에 있다.** 하루 500회. 평가와 데모가 키를 나눠 쓰면 저녁에 데모가 죽는다 (키를 갈랐다).
- **팀 버전에 있고 여기 없는 것**: 인증 · 인가 매트릭스 · OpenTelemetry 관측 · LangGraph 흐름 제어 ·
  열 개 능력(`orchestration/adapters/`) · 골드 80 라우터 벤치마크. 여기는 능력 둘짜리 오케스트레이터다. 그게 요점이기도 하다 — 둘만
  붙여도 안전장치가 무력해지는 걸 보여주는 데는 둘이면 된다.
